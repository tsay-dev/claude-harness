# ADR-0002 契約チェッカーのパーサを自前実装し、受理する YAML を厳格サブセットに限る

## Context

ADR-0001 で契約を harness 独自 YAML に移すと決めた。この形式の妥当性を判定するのは `.claude/tools/spec-lint/`（拡張して 1 本のまま使う）だが、現行の spec-lint は YAML を正規表現の行スキャンで見ている。この方式では次のような構造的な検査がそもそも書けない。

- `requires:` を宣言した操作に、対応する権限拒否の `errors:` があるか
- `transport` が `http` 以外なのに `wire:` が書かれていないか
- `errors[].code` が `_shared` の `errorCodes` に定義されているか
- `examples` の各ケースが、その操作の `request` / `response` のキーと噛み合っているか

今回の設計変更の動機そのものが「AI に全文を読ませて判定させるのではなく、チェッカーを走らせて結果だけ受け取る」ことにある。行スキャンのままではその動機を満たせない。本当のパース（AST）が土台として要る。

## Decision

**受理する YAML 構文を意図的に狭い厳格サブセットに限定し、そのサブセット専用のパーサを `.claude/tools/spec-lint/` に自前で実装する。**

受理するのは、マップ、シーケンス、フロースタイルのマップ / シーケンス、スカラ（文字列 / 数値 / 真偽 / null）、コメントのみ。次は構文エラーとして err にする。

- **アンカーとエイリアス（`&` / `*`）** — 共有は `_shared/components.yaml` の `$ref` を通す、という既存の分担がある。ファイル内で値を使い回す経路を構文レベルで塞ぐ。
- **複数行スカラ（`|` / `>`）** — 長文は `spec.md` に置く、という契約の負のリストがある。契約に長い散文が書けない状態を構文で作る。

つまり**サブセットを狭くすること自体が検査になっている**。パーサが受理しないことで、契約が守るべき分担がフォーマットの入口で強制される。

## Consequences

**得られるもの**

- 依存ゼロのまま AST が得られ、構造的な検査（`requires` ↔ `errors` の対応、`wire` の transport 適合、`errors[].code` の参照解決、`examples` のキー整合）が素直に書ける。
- 人間可読で、テンプレートのガイダンスコメントも載る。
- 検査結果が環境によらず均一になる。オフラインでも CI でも同じ判定が出る。
- パーサが受理する構文を我々が決められるため、契約に持ち込ませたくない書き方を「未対応」ではなく「エラー」として明確に落とせる。

**代償と今後の制約**

- **パーサを保守する責務を負う。** ただし受理する構文を我々が決めている以上、対象は固定であり、YAML 仕様の全面追従は不要。フォーマットを広げるときだけパーサを触る。
- **一般の YAML ツールで契約を読むと、我々が禁じた構文も通ってしまう。** 判定の正は常に spec-lint であり、エディタや他のツールが通したことを根拠にしてはならない。
- **`examples` が JSON Schema に適合するかの完全な検証はできない。** キーの整合と必須項目の有無までは見るが、`minLength` などの制約充足は検査しない。ここは structure-oracle の意味的判断に残る領域と重なるため、当面は許容する。必要になったら JSON Schema の検証器も自前で狭く実装するか、この判断を supersede する。
- structure-oracle は残すが、任務を意味的妥当性（この境界で GWT を満たせるか、概念的に欠けているエラーケース、操作の粒度）に絞る。機械が見た項目を再検査させない。「建てる ≠ 裁く」（CLAUDE.md §1）は保たれる。

## 却下した選択肢

- **契約ファイルを JSON にする。** `JSON.parse` で確実にパースでき、依存ゼロで実装コストもほぼゼロ。退けた理由は、コメントが書けないこと。現行テンプレートはガイダンスコメントがフォーマットの SSOT そのもの（CLAUDE.md §2）であり、LLM の既知フォーマットでなくなった以上（ADR-0001）その伝達手段への依存はむしろ上がる。それを丸ごと失うのは本末転倒。
- **`npx` で js-yaml / ajv をオプショナル実行する。** examples が宣言した JSON Schema に適合するかまで検証でき、検査力は最大。contract-author が既に `npx -y @redocly/cli` をこの作法で呼んでいる前例もある。退けた理由は、ネットワーク依存で保証が不均一になること。オフラインや CI で黙ってスキップされると「チェッカーが通った」の意味がホストごとに変わり、機械検査を信頼の土台に据える今回の設計と噛み合わない。
- **npm 依存として js-yaml / ajv を入れる。** 保証は均一になるが、SwiftUI プロジェクトに `node_modules` を持ち込むことになる。共有ハーネスがホストの構成を縛る（CLAUDE.md §0）。
