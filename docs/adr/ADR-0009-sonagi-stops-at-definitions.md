# ADR-0009 sonagi は制作定義とプロンプトまでを出力し、画像・音声・動画の実体を生成しない

## Context

動画制作スキル `sonagi` は、企画（`brief.yaml`）から公開パッケージまでを L0→L4 の階層で導出する。
この鎖のどこを出口にするかで、スキルの性質が根本的に変わる。

- **実体まで作る**なら、画像生成 API・TTS・レンダラ（ffmpeg / Remotion）への依存が入る。
  同じ入力でも出力が変わり（サービス側の非決定性）、鍵の管理・失敗リトライ・実行時間が設計に乗る。
- **定義で止める**なら、出力はテキストと JSON だけになり、同じ入力に対して同じ出力構造が返る。

harness の他のスキル（`translate-manga-ko-ja`）は同じ問いに対し「人間が必ずチェックする前提で、
チェックコストを最小化する成果物までを出し、`final/` には踏み込まない」という線を引いている。

## Decision

**出口は定義とプロンプトまでとする。** 外部サービスを叩かず、`.png` / `.mp3` / `.mp4` を1つも生成しない。
レンダリングはスキルの外（人間または別ツール）の仕事とする。

この線は rules（`rules/sonagi/overview.md` の「純粋関数的な契約」）に置き、
画像プロンプトは**サービス非依存の中立形式**（英語の構造化記述、`--ar` や `::` などの重み付け記法を禁止）とする。
機械検査 C11 が、日本語混入とサービス固有記法を弾いて線を守る。

## Consequences

- 同じ入力に対して同じ出力構造が返るので、機械検査（`tools/sonagi`）が全成果物に当たり、評価も再現する。
- 画像生成・TTS のサービスを乗り換えても、rules も agent も書き換えずに済む。
- **人間の作業が1段残る。** プロンプトを各サービスへ貼り、素材を集め、レンダリングする手間はなくならない。
  「1コマンドで動画が出る」体験は得られない。
- **プロンプトの良し悪しを、実際の生成物で検証できない。** 出来上がった絵を見て直すループがスキルの中に無く、
  そこは人間が担う。

## 却下した選択肢

- **素材まで生成し、結合はしない**: 画像生成と TTS を実際に叩いて `assets/` に PNG / MP3 を落とす案。
  API 鍵・課金・失敗リトライ・生成物の非決定性が一度に設計へ乗り、
  「同じ入力→同じ出力」が崩れてテストが不安定になる。得られるのは中間物だけで、割に合わない。
- **mp4 まで一気に通す**: 価値は最大だが、上記に加えてレンダラの環境依存（ffmpeg のバージョン、フォント、
  コーデック）がホスト側に持ち込まれる。harness は「プロジェクト固有の事情を持ち込まない」ことを核にしており、
  レンダラの選定はホストの都合である。
- **定義まで出しつつ、timeline.json を特定レンダラの入力形式に合わせる**: 将来レンダラを足すときの手間は減るが、
  レンダラを1つ選ぶ判断を今する必要があり、選ばなかった側では JSON が無意味になる。
  中立形式にしておけば、変換は後から書ける。
