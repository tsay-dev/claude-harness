# ADR-0016 秘密は追跡されるファイルから読まない。設定と秘密を別の器に分け、課金前に preflight で確かめる

## Context

`render-media` は外部サービスを叩いて課金を発生させるが、**API キーの管理を何も決めていなかった**。
ホストの実装（`sonagi/tools/render/render.py`）は `os.environ` を直読みするだけで、
**その環境変数をどこから供給するかは人間の暗黙知**として残っていた。

素直な案は「プロジェクトに config ファイルを置き、そこでキーを管理する」である。
しかしこれは、**追跡の要求が正反対の2つを1つの器に入れる**。

- **設定**（サービス・モデルID・声ID・解像度）は**追跡したい**。
  この型は `timeline.actual.json` を定義と別物として残すほど再現性に金を払っており、
  設定が追跡されないと「なぜこの回だけ絵が違うのか」が後から追えない。
- **秘密**（API キー）は**追跡してはいけない**。

同じ器に入れると、どちらを立てても片方が壊れる。gitignore すれば設定の再現性が消え、
穴埋めのための `config.example.yaml` は**必ず本体とズレる**。追跡すればいつかキーが入る。

そしてこのパイプライン固有の事情がある。**エージェントがファイルを読む前提で動いている。**
`media-checker` は `Read` / `Bash` / `Grep` / `Glob` を持ってホストを歩き、orchestrator も入力確定で
ディレクトリを見る。**平文のキーがリポジトリ内のファイルに在ると、エージェントの視野に入る**——
grep の巻き添えで会話に出るし、成果物に書き出される経路もある。
git に漏れるリスクより、こちらのほうが日常的に起きる。

もう1つ、課金に直結する穴があった。`render.py` はキーが無いとき **audio 工程に入ってから**落ちるが、
skill の工程順は `画像 → 音声 → …` である。つまり**画像を生成して課金した後に、音声のキーが無くて止まる**。
skill は工程1で「課金の規模を提示して承認を得る」と定めているのに、
**その承認の前提（そもそも全工程を走れるのか）を確かめていなかった**。

## Decision

**秘密は追跡されるファイルから読まない。設定と秘密は器を分ける。揃っているかは課金前に確かめる。**

- **アダプタは、git に追跡されるファイルから秘密を読まない**（アダプタ契約に追加）。
  禁止だけを定め、**供給経路は縛らない**。ホストが `.env` を読んで `os.environ` に載せてもよい。
  「環境変数から受け取れ」ではなく「追跡されるファイルから読むな」と書くのは、
  **供給手段を将来変えても契約が生き残る**ためである。
- **設定と秘密は粒度も違う。** 設定はチャンネル単位まで割れる（声はすでに `channel/voice.md` で割れている）が、
  **キーはプロジェクト単位**である（サービス契約は1つ）。粒度の相違そのものが、器を分ける裏付けになっている。
- **`<adapter> <video_dir> preflight` を必須サブコマンドにする。** 必要なキーと設定が揃っているかを、
  **課金の承認より前に**確かめる。skill は工程1でこれを叩く。
- **harness は config のファイル名もキー名もスキーマも定めない。** ハーネスはサービス数も設定項目も知らない。
  形を決めるのは越権であり、決めるのはホストである。

`adapter.md` の「共有ハーネスにサービス固有の実装を置かない」は変わらない。
今回足したのは**禁止と、課金前に止まる点**の2つだけである。

## Consequences

- 設定の再現性と、秘密の非追跡が両立する。config を読んだエージェントが得るのは、キーの値ではなく在り処だけになる。
- **課金してから止まる事故が消える。** 承認の前提が承認の前に確かめられる。
- **preflight の必須化は、既存アダプタを契約違反にする。** ホストが `sonagi` 1つだけの今が最も安い。
- **「追跡されるファイルから読まない」は機械で確かめられない。**
  git の追跡状態に依存する契約であり、**`.gitignore` し忘れた `.env` は、契約を満たしているように見えて満たしていない**。
  この線を守るのは最終的に人間である。
- **preflight が確かめられるのは「在ること」だけである。** キーが有効か・残高が足りるかは、
  実際に叩くまで分からない。**残高切れによる途中終了は依然として防げない。**
- harness が config の形を定めないので、**ホストが増えれば形はバラバラになる**。
  別プロジェクトのアダプタを読むとき、毎回読み直しが要る。

## 却下した選択肢

- **config ファイルにキーを直接置く**（当初案）: 最も素直で、手順が1つで済む。
  しかし設定と秘密は追跡要求が正反対で、**どちらを立てても片方が壊れる**。
  加えて、エージェントがファイルを読む前提のこのパイプラインでは、
  平文キーが日常的にエージェントの視野に入る。git 漏洩より頻度が高い。
- **config を gitignore し、`config.example.yaml` を置く**: 広く使われている形。
  しかし example は本体とズレるのが常であり、何よりも**設定まで追跡から外れる**ので、
  この型が一番払っている再現性が消える。
- **キーを OS キーチェーンに置く**: 平文がディスクに残らず最も漏れにくい。
  しかし OS 依存でアダプタが太り、CI や別マシンへの持ち出しが面倒になる。個人運用に対して重い。
- **供給を `direnv` 等の外部に任せる**: アダプタは `os.environ` しか見ず、実装は最も純粋になる。
  しかし環境構築が人間の暗黙知として残り、新しいマシンやエージェント実行で踏む。
  **「手順を知らなくても動く」ほう**を採った。
- **preflight を任意のサブコマンドにする**: 既存アダプタが契約違反にならない。
  しかし「無ければ飛ばす」に落ちるので、**一番守りたい課金事故がちょうど守られない**。
- **キー欠落のチェックを skill 側に置く**: アダプタを変えずに済む。
  しかし skill が「どのキーが要るか」を知ることになり、**サービス固有の事情が型に漏れる**。
  `adapter.md` が引いた線（型はサービスを知らない）をそこで越える。
