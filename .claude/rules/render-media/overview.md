# 📦 全体像・思想（定義 → 実体）

> 制作定義（台本・素材プロンプト・コマ定義・タイムライン）を、実際のメディアに変換する型。
> ここは**この型の不変の核**（最初に読む）。アダプタの契約は [adapter.md](adapter.md)、
> 実測でタイムラインを引き直す作法は [retime.md](retime.md)。
> 実行手続きは skill [render-media](../../skills/render-media/SKILL.md)。

## なぜ企画と生成を分けるか

**企画は純粋関数にできるが、生成はできない。**

企画側（[produce-video](../../skills/produce-video/SKILL.md) など）は、同じ入力から同じ出力構造を返す。
だから検査でき、評価でき、再現できる。生成側は違う——外部サービスを叩き、課金が発生し、
同じプロンプトから毎回違う絵が出て、失敗する。

この2つを1つのスキルに混ぜると、**企画側まで再現しなくなる**。分けておけば、
非決定性は生成スキルの中だけに閉じ込められ、企画側は純粋関数のまま残る。

そしてもう1つ。**生成は媒体を選ばない。** 「定義を実体にする」という工程の形は、
動画でもポッドキャストでもスライドでも同じである。分けておけば、企画側を差し替えるだけで応用できる。

## 🔒 この型の核

- **入力は企画側が出した定義だけ。** 定義を書き換えない。実測が定義とずれても、
  **定義は定義のまま残す**（それは予測であって、実測ではない）。
- **出力は `media/` 配下の固定名だけ。** 何が生成済みかは、**ファイルの存在**が表す。
  台帳を持たない（持つと必ず実体とずれる）。
- **在るものは作り直さない。** 課金が発生する工程なので、これは規律ではなく実害の回避である。
  作り直したいものは、そのファイルを消す。それが唯一の再生成の指示方法である。
- **サービス固有の実装はアダプタに閉じる。** この型はアダプタの契約だけを知り、
  どのサービスをどう叩くかは知らない（[adapter.md](adapter.md)）。

## 工程と依存

順序には理由がある。**入れ替えてはならない。**

| 工程 | 何を作るか | なぜこの位置か |
| --- | --- | --- |
| **1. 画像** | コマごとの静止画 | 動画クリップの開始フレームに使えるので、動画より先 |
| **2. 音声** | ナレーション | **尺の実測値がここで初めて手に入る** |
| **3. 再計時** | 実測タイムライン | 以降の工程が使う尺が、ここで予測から実測に変わる |
| **4. 効果音・BGM** | 音の素材 | 総尺が確定してから（BGM の長さは総尺に依存する） |
| **5. 動画** | コマごとのクリップ | 実測尺で作る。画像を開始フレームに使える |
| **6. 結合** | 完成物 | 全部揃ってから |

**音声を画像より先にしない。** 画像は尺を持たないので、順序を入れ替えても情報は増えない。
**再計時を後ろにずらさない。** ずらすと、予測の尺で動画クリップを作ってしまう。

## 🚫 実体を見ずに完了を報告しない

生成 API は「成功」を返しながら、**中身が壊れたファイル**を寄こすことがある。
サイズがゼロ、想定と違う長さ、想定と違うアスペクト比。

**生成したファイルは必ず実測する**（長さ・サイズ・寸法）。
「API が 200 を返した」は「作れた」ではない。
