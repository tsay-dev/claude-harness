# 📦 実測でタイムラインを引き直す（音に画を合わせる）

> 企画側の尺は予測である。実体が手に入った時点で、実測に基づく別のタイムラインを起こす。
> なぜこの位置かは [overview.md](overview.md)。
> 実行手続きは skill [render-media](../../skills/render-media/SKILL.md)。

## 予測と実測は必ずずれる

企画側の尺は「話速 × 文字数」で配られる。話速は実測値だが、**平均である**。
コマ単位では上下にばらつく——実測では **RMS 0.5秒、最大 1.3秒**のずれが出た。

面白いのは、**合計はよく合う**ことである（56.0秒の定義に対し実測 56.5秒、誤差 0.9%）。
過不足が打ち消し合うためで、これは企画側の尺予算が**動画全体に対して**成立し、
**1コマごとには成立しない**ことを意味する。

## 🔒 音に画を合わせる

ずれをどちらに寄せるかは、**音声を基準にする**。

**視聴者が気づくのは音の途切れであって、総尺の 0.5 秒差ではない。**
画に合わせて音を切ると、語の途中で切れる。無音を足すと、間が不自然になる。
画は静止画でもクリップでも、長さを変えても破綻しない。

したがって: **各コマの尺は、そのコマのナレーション音声の実測長とする。**

## 🚫 定義を書き換えない

実測タイムラインは `media/timeline.actual.json` に**別ファイルとして**書く。
企画側が出した `timeline.json` は**そのまま残す**。

理由は2つある。**定義は予測として正しく、実測と食い違うこと自体は欠陥ではない**こと。
そして、企画側を再実行したときに実測が混ざっていると、**何が予測で何が実測か分からなくなる**こと。

```json
{
  "basis": "measured-audio",
  "total_duration_sec": 56.48,
  "planned_total_sec": 56,
  "scenes": [
    { "scene_id": "SC-01", "start_sec": 0.0, "duration_sec": 5.6,
      "planned_sec": 6, "drift_sec": -0.4 }
  ]
}
```

**`drift_sec` を必ず持たせる。** ずれの大きいコマは、台本の文字数が話速の平均から外れた場所であり、
**次の回の書き方に効く情報**である。捨てるとその学習が起きない。

## ずれが大きすぎるとき

1コマのずれが**2秒を超える**なら、それは話速のばらつきではなく**台本側の問題**である
（文字数の見積もり違い、読みの指定漏れ）。実測で押し通さず、人間に報告する。

## 🔒 再計時はマスター言語で1度だけ（多言語）

多言語の動画でも、**実測タイムラインを引くのはマスター言語の音声に対して1度だけ**である。
言語ごとに再計時してはならない。

理由は配信の形にある。**映像は1本で、そこに全言語の音声トラックが載る**。
映像のコマ割りが言語ごとに違えば、そもそも1本にならない。
だからずれを吸収する向きが逆になる——マスターでは「音に画を合わせ」たが、
**翻訳では「マスターの窓に音を合わせる」**。

- 翻訳音声がコマの窓に**収まらない**のは、実測のばらつきではなく**翻訳（定義）側の欠陥**である。
  速度を変えて詰め込まず、そのシーンの訳の直しとして報告する（窓の長さは企画側の文字予算が予測している）。
- 翻訳音声が**短い**のは欠陥ではない。余りは間として無音で埋まる。
